## 建议的固定工作流

1. **开发**：从 fork 的 `main` 创建功能分支，小范围修改，运行相关测试；提交并推送功能分支。
2. **检查**：通过 PR 合入 `main`，以 CI 通过的 `main` 提交为发布对象。当前未提交的部署文件改动需先审查、测试并单独纳入 PR，才会成为实际发布内容。
3. **构建版本**：在选定提交上创建新的 `v*` 标签并推送。`publish-image.yml` 会运行 Go 与前端测试，并构建 `linux/amd64`、`linux/arm64` 镜像到 GHCR。不要复用或移动已发布标签。
4. **部署**：在 VPS 的 `/opt/dujiao-next` 保留生产专用的 `.env`、`config.yml` 和数据目录。将 `APP_IMAGE` 指向明确的版本标签，先拉取镜像；更新前备份配置、SQLite 数据、上传文件及 Redis 数据；再用 Compose 启动并检查健康接口、日志和业务流程。
5. **恢复**：保留旧镜像版本及更新前数据备份。若版本包含数据库迁移，恢复时同时使用旧镜像与相应数据备份，不能仅把镜像标签改回去。定期将备份复制到 VPS 之外并演练恢复。

## 首次部署前的决定与检查

1. 确认 VPS 系统版本、CPU 架构、SSH 登录方式，以及是否已运行旧实例。已有实例应先盘点并备份现有 `config.yml`、数据库和上传文件，保留已有密钥与后台路径。
2. 确认最终域名是否为 `store.kanoapi.top`，DNS 是否指向 VPS，80/443 是否可达；模板里已写入该域名。
3. 决定业务改动是否允许公开。当前 fork 公开；若要保密，需先决定代码仓库与镜像的可见性，并为 VPS 配置读取私有 GHCR 镜像的凭据。公开镜像可匿名拉取，但不能把生产密钥打进镜像。
4. 合并部署 PR 后发布首个实际标签，确认镜像发布成功，再按照 `deploy/README.md` 安装 Docker、Compose、Nginx、配置生产文件与 HTTPS。安装步骤要按 VPS 实际发行版选择。
5. 首次启动后检查 `/health`、后台登录、商品浏览、测试下单及异步任务；删除配置中的初始管理员密码并重启应用。

## Debian 首次部署补充检查（2026-09-28）

- `store.kanoapi.top` 当前解析到 Cloudflare 代理地址；从外部请求 `https://store.kanoapi.top/health` 返回 HTTP 521。Cloudflare 官方解释该状态通常是源站拒绝连接。全新部署尚未启动服务时这与预期一致，但单凭代理后的 DNS 记录无法核对源站 IP。
- 先在 Cloudflare 控制台核对该域名的 A/AAAA 记录指向 VPS 公网地址；若 VPS 没有 IPv6，不要保留指向其他源站的 AAAA 记录。确认服务器安全组及防火墙允许所需的 80/443 访问。
- 按 [Docker 的 Debian 官方安装步骤](https://docs.docker.com/engine/install/debian/)为 Debian 13 安装 Docker Engine 与 Compose 插件，随后按 `deploy/README.md` 部署应用、主机 Nginx 和 HTTPS。
- 若使用 Cloudflare 代理，源站仍须能在所选 SSL/TLS 模式对应的端口接受连接；证书安装后核对 HTTPS 到源站的配置。参见 [Cloudflare 521 说明](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-5xx-errors/error-521/)。
- 当前 Nginx 模板把连接对端的 IP 传给应用。经 Cloudflare 代理时，该地址默认是 Cloudflare 边缘 IP；如业务限流或审计需要真实访客 IP，应在上线前按 [Cloudflare 的 Nginx 指引](https://developers.cloudflare.com/support/troubleshooting/restoring-visitor-ips/restoring-original-visitor-ips/)配置可信代理网段，并维护其更新，避免直接信任任意请求头。
